# V3-01-27 — Acceptance Lineage Identity Contract

## Decision

Status: **SOURCE-ONLY / ZERO-CALL / OWNER G-08 PENDING**.

V3-01-27 fixes the identity contract instead of minting a procedural RC tag merely to obtain two
unused operation slots. The exact base is governance `main`
`c0f051c866d329544486e5e757349f0543ace980`. This PR intentionally does not create a new RC,
gate bundle instance, acceptance window, operation authority or provider execution.

The RC-16 original W1 lineage remains retired: Operation 1 is consumed/failed/review-required after
the provider returned `credit_balance_exhausted`; its Operation 2 remains retired and locked. That
historical receipt, operation ID, cost semantics and verdict are not changed.

## Root cause

The existing operation key was derived only from:

`RC tag + provider + capability + slot 1/2`

This correctly prevented duplicate execution, but it also allowed only one two-slot acceptance
lineage per executable RC. A quota failure consumed slot 1 and made slot 2 unsuitable as the first
run of a new consecutive pair. Creating an otherwise-identical RC would hide this acceptance
identity limitation rather than repair it.

## Canonical identity

New gate bundles use bundle `version=2` and must carry both:

- `acceptance_lineage_sequence`: strict JSON integer in the inclusive range 1–9999;
- `acceptance_lineage_id`: `al-{sequence:04d}-{64 lowercase SHA-256 hex}`.

The digest is calculated from canonical UTF-8 JSON containing exactly:

- contract marker `v3-01-acceptance-lineage-v1`;
- exact RC tag and 40-character commit;
- provider key, model and capability;
- lineage sequence.

Keys are sorted, Unicode is retained and separators are fixed to `,` and `:`. The sequence is the
only bounded discriminator; no free-form label, nonce or operator-supplied text is trusted. The
loader re-derives the ID and rejects a malformed, tampered or cross-scope value.

The corresponding operation identity is:

`v3-01-{rc}-{provider-capability}-{acceptance_lineage_id}-call-{slot:02d}`

Slots remain exactly `(1, 2)`. Two sequences under one RC therefore have distinct operation IDs,
while both runs inside one lineage share an immutable identity and differ only by slot.

The machine-readable contract is
[V3-01-27-ACCEPTANCE-LINEAGE-IDENTITY.v2.json](contracts/V3-01-27-ACCEPTANCE-LINEAGE-IDENTITY.v2.json).

## Binding and fail-closed boundary

The lineage is independently bound into:

1. the strict v2 gate bundle;
2. canonical execution-scope SHA-256;
3. both allowed operation IDs;
4. the trusted provider call context;
5. attempt and execution receipts;
6. durable operation and attempt ledger rows;
7. deployment/runtime pin `PROVIDER_GATE_EXPECTED_ACCEPTANCE_LINEAGE_ID`.

The loader requires the runtime pin for every v2 bundle. A missing, stale or wrong pin is rejected.
The provider controller also compares the call-context lineage with the verified scope before any
budget reservation. An operation from an earlier lineage is not allowlisted in the current lineage;
an operation with the right key but a wrong lineage marker is rejected as
`ACCEPTANCE_LINEAGE_MISMATCH`.

Repository writes preserve the same lineage on the operation, attempt and completion paths. A
mismatch between a reserved operation and its attempt or completion raises before evidence can be
recorded under the wrong lineage. Migration `0014_v3_01_27` adds nullable ledger fields: new v2
operations carry the canonical ID, while historical rows remain `NULL`.

## Historical compatibility

Bundle `version=1` is the immutable historical representation:

- lineage fields remain absent/`None`;
- legacy operation IDs are generated byte-for-byte as before;
- lineage fields are omitted from legacy execution-scope hashes;
- existing static bundle SHA-256 values, receipts and evidence files are not rewritten;
- nullable model and database fields allow historical receipts/rows to load unchanged.

A v1 bundle cannot claim a lineage, and a runtime configured with a lineage pin cannot load v1.
This prevents a legacy bundle from masquerading as a new lineage while retaining audit access to
past evidence.

## Enforcement matrix

| Case | Result before provider boundary |
|---|---|
| Valid v2 ID derived from exact RC/provider/model/capability/sequence | Accepted on offline path |
| Second sequence under the same RC | Distinct two-slot operation IDs |
| Missing ID or sequence | Reject |
| String/bool/out-of-range sequence | Reject |
| Tampered digest or sequence prefix | Reject |
| Wrong RC tag/commit/provider/model/capability | Reject |
| Missing/stale runtime lineage pin | Reject |
| Legacy operation ID in a v2 scope | Reject |
| Wrong lineage in call context | Reject before reservation |
| Repeated operation in the same lineage | Durable duplicate protection rejects |
| Historical v1 bundle/receipt/ledger row | Loads without mutation |

## Unchanged controls

V3-01-27 does not change:

- W1 prompt profile, prompt hash or provider request content;
- provider/model/language choice;
- 90-second provider and 120-second controller timeout envelope;
- 500 VND per-operation or 1,250 VND window limits;
- attempt, concurrency, retry or fallback limits;
- WAV, transcript or RightsRecord hashes and permissions;
- WER ≤15% or critical-term recall 8/8;
- timestamp and `PositiveDurationTranscript` semantics.
