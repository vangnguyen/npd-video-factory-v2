# Response-bound posting-time evidence

Wave 10/12 increment on the preserved North Star branch. This adds read-only timestamp normalization to the existing scoped YouTube/TikTok collectors and channel-learning path. No live migration, credential acquisition, external call or publication is enabled.

`publication-time-evidence-v1` records provider/platform, exact publication and remote-post hash, target-binding hash, successful response hash/operation, observation clock, transport flags, provider field, reported timestamp and semantic availability. Timestamp capture checks the authenticated account and exact video before collecting. Feature capture and learning verify the same response observation, collection clock, target and transport; mismatches remain unavailable. Missing, malformed, coerced, future or ambiguous values never use receipt, queue, upload or collection times as substitutes.

TikTok reads request `create_time`. Its documented integer UTC epoch value represents when a video was posted. A valid value becomes `verified_posted_at` with basis `provider_posted_time`; this does not prove first public exposure, public accessibility or an audience-optimal time. See the [official TikTok Video Object](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-object).

YouTube's `snippet.publishedAt` can represent upload time for private, unlisted and members-only videos. The documented status fields do not establish all these timestamp semantics for our read path. The current collector preserves a valid reported timestamp with an explicit ambiguity reason and leaves verified publication time null, including a later public status. `status.publishAt` is a schedule and is never substituted. See the [official YouTube video resource](https://developers.google.com/youtube/v3/docs/videos). Removing this conservative limitation requires a separate evidence-backed semantics design.

Frozen feature metadata stores the normalized timestamp and its typed evidence. Verified UTC timestamps retain their offset on SQLite reads; historical fixture/unverified read serialization is preserved. Prior analytics rows and immutable channel-learning snapshots are unchanged. No persistence schema or model-digest defaults are added.

Channel learning accepts a posting-window feature only when feature/metric evidence and the persisted UTC time match exactly. Groups use UTC weekday and four-hour windows, explicitly labeled `provider-posted`. Unknown values are excluded from both sample and control groups. Existing minimum independent-post, retention/completion, compatible scope and assessment-basis requirements apply. A timestamp alone cannot create a winner, sufficiently supported recommendation or forecast. Snapshot scope records timezone, bucket size and count of compatible observations with verified posted times. Studio distinguishes missing time from provider-posted history and identifies mock data.
