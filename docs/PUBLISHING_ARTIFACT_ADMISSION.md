# Verified publishing artifact bytes

`PublishingArtifactGuard` is an inert worker component. It requires the separate current publish consent and durable dispatch binding, obtains an owned private copy of the approved output, runs the existing `FullProductionQC`, and returns checksum-verified byte ranges. It does not enable publishing or issue an upload request.

The guard rechecks current Owner identity, approval/QC, timeline/audio/subtitles, metadata and source rights through the journal before reading storage and after inspection. The artifact object key must belong to the same workspace/project and configured storage provider. Only a final render profile is admitted; review profiles fail. Actual QC checks dimensions against the canonical profile, duration/fps against the saved timeline, H.264/AAC/48kHz, audio/silence/clipping, A/V sync, black/freeze/decode and sampled pixel quality. Original subtitle/timeline QC evidence remains part of the approved production binding. Its publishing-blocked field is retained: media quality facts alone confer no authority to publish.

Storage reads are bounded by the registered exact size and 512 MiB internal limit. Local files/ancestors reject links, junctions and multiple hardlinks. S3 reads require exact ContentLength, at most 5-second connect/30-second read timeouts and a one-attempt retry configuration, close their stream on every outcome and reject excess/short bytes. An opt-in `publishing_storage_config()` can be supplied to the existing S3 constructor; other storage defaults are unchanged. SDK sensitive logging is suppressed within the private operation's context; unrelated logs remain. No bucket creation, signed URL fallback, object discovery or credential bootstrap is performed by the reader. Actual SDK regional redirects/endpoint pinning and configured network policy still need production acceptance; a retry setting alone does not certify them.

Each copy uses a new private work directory and exclusive file creation. Missing work root, storage profile, media tools or valid evidence fails closed. A cancellation flag stops the copy after the current bounded read. Repeated task cancellation waits for that owned thread before cleaning its directory. Cleanup only removes the component's new temporary directory, never the original object, accepted render or configured root.

MP4 magic, size and whole-file SHA256 must match before QC. A private in-memory SHA256 manifest covers 256 KiB blocks. Every range read verifies all touched blocks, including unaligned ranges, then returns the exact approved bytes. Same-size changes are detected even if timestamps are preserved. A closed snapshot or invalid/noninteger/oversized range fails. The snapshot is internal worker state with no path/content representation in public APIs.

Tests use actual owned files, conditional approval persistence and SDK metadata, but their QC/S3/identities are explicit fixtures. The separate five-export rehearsal uses a fresh 1080×1920, 30fps H.264/AAC synthetic test-pattern/sine MP4 and actual `FullProductionQC`. Seventeen ranges reconstruct all 4,256,257 bytes exactly. Its disposable stored copy is then corrupted and refused before QC/wire; the original synthetic MP4 is retained unchanged. This is actual local media admission, not speech/semantic quality, a Video Factory final render, Owner UAT or one of the final A/B/C acceptance bundles.

Remaining work includes the durable upload worker/provider adapter, atomic admission across concurrent project edits, orphaned session recovery, OAuth/key lifecycle, costs and Native publishing UI. The guard rechecks bindings but cannot prevent an edit immediately after a transaction or cancel a provider request through a database lease. Real S3/provider/production acceptance remains separate. All publishing flags/factories stay disabled/contract-only.

The S3 reader follows official [GetObject](https://docs.aws.amazon.com/boto3/latest/reference/services/s3/client/get_object.html) response/stream metadata and [botocore Config](https://docs.aws.amazon.com/botocore/latest/reference/config.html) timeout/retry settings. It uses existing object-storage and production-QC components instead of changing the canonical timeline or introducing another production database.
