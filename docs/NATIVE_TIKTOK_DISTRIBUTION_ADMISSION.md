# Native TikTok publication admission

Historical milestone 270: this document and its original evidence describe admission-only behavior at that commit. The later [TikTok execution increment](NATIVE_TIKTOK_PUBLISHING.md) implements the upload/status backend; startup/Studio publishing and genuine provider acceptance remain incomplete. Original milestone evidence is retained unchanged.

The creator review previously ended at an unsent draft. This increment connects an exact reviewed draft to the existing Native publication journal, dry-run validation, current Owner identity, separate finite publication approval, local revocation and explicit prepared-grant renewal. It does not complete TikTok transfer/status execution or original Wave 9 acceptance.

The new request is tagged `native-official-tiktok-publication-request-v1`. It supplies the project revision, original dry-run ID/hash, creator draft ID/hash, publishing profile/configuration hash and an idempotency key. Metadata and post choices come from the immutable reviewed draft. The completed TikTok dry run must have exactly the same metadata and current approved final. The stored snapshot is tagged `native-official-tiktok-publication-snapshot-v1`; existing YouTube request/snapshot schemas and hashes retain their behavior.

Admission checks the owned draft's original account/creator responses and cost links, target, credential ciphertext fingerprint, document revision, physical final/hash/QC/review, platform validation and structured TikTok choices. Creating a new publication requires the original creator read to remain within its explicit consent window. A draft, successful account read or dry run never provides publication authority. Approval creates a separate current Owner grant; expiry, revocation, changed source, cancelled creator proof, mismatched metadata or configuration prevent admission. The original creator read cannot be renewed by a publication grant. A future worker must fetch current creator constraints before initialization under separately authorized publishing execution.

`NativeTikTokPublishingFactory` has a distinct protected companion registry bound to the creator configuration and pinned credential ciphertext. Raw enablement flags default to false. Registry/discovery/admission/history do not decrypt the credential or contact a provider. The composition API accepts only the exact owned creator service/factory/workspace/root. This registry is not yet wired into CLI/server startup or Studio publishing controls.

Execution is explicitly unavailable at this milestone: `execution_supported=false`, `external_actions_enabled=false` and real networking disabled. A configured mock factory means only the admission fixture is configured. The existing YouTube worker and direct dispatch-intent method reject TikTok before credential/session load, cost claim or wire. No YouTube request or observation is substituted for TikTok. Completing Native TikTok initialization, protected async job/session storage, sequential transfer, uncertain-result reconciliation, processing observations, qualified receipts, queue/Studio integration and real-provider acceptance remains required. No `publish_id`, post ID, URL or publication receipt is invented.

Historical public reads validate the original stored draft, response/cost and render links without a current registry, credential, provider or Owner token. The retained fixture demonstrates public backup/restore and a separate process replay of all 27 journals, the original project/final and publication snapshot. DPAPI and SQLite run locally; TikTok responses, platform acceptance, media bytes and human approvals are explicit fixtures. The final is nonplayable and does not prove media QC, Owner UAT or full Mode A/B/C acceptance.
