# Analytics scheduling and queue safety

Scheduled collection remains disabled by default. Admission now applies the scheduling switch to any supplied `scheduled_for`, including requests labelled initial or manual refresh. The processor checks the current switch again before collection. The configured official runtime checks it before each read, alongside the existing scope, account, credential, receipt, attempt and cost gates. Revocation can stop subsequent reads; a read already sent is recorded honestly and is not undone. A disabled scheduled job terminates as `not_configured` without a metrics snapshot.

New schedule, retry and observation timestamps must carry a timezone and are normalized to UTC before persistence. This preserves their exact instant when SQLite removes timezone metadata. Their read projection includes UTC explicitly. Original request fingerprints retain the submitted representation for existing idempotency semantics. Historical rows/exports are not rewritten or recertified; a legacy non-UTC scheduled row cannot be repaired without its original offset evidence and must be reviewed before enablement.

Provider Retry-After and the local exponential backoff are combined without shortening the provider's minimum interval to the local cap. Typed rate-limit delays accept positive integers up to one day; invalid values fail. Official response parsing retains its separate, stricter bounded delay contract. Backoff does not alter historical snapshots or invent metrics.

Due claims are limited to 100 jobs per tick, with deterministic ordering and conditional status/attempt/due-time updates. PostgreSQL uses skip-locked selection; SQLite uses the conditional update to reject a competing reader's stale selection. Competing ticks may select the same first page; the losing tick does not claim it again and later ticks advance the remaining page. No duplicate collection follows a duplicate queue message because worker claims and completed snapshots remain fenced by stable sync identity.

An API admission can persist a queued job before Redis becomes available. An explicit retry with the same idempotency key now re-enqueues that same job. The worker scheduler also checks a bounded page of durable queued jobs, so a failed enqueue is recoverable on a later tick without restart. Redis queue admission checks both pending and processing lists in one Lua operation. Each tick considers at most 100 newly due and 100 durable pending IDs. Queue failures retain database state and emit a fixed log category without raw connection errors. Cancellation propagates. Existing startup recovery remains available; a complete runtime/Redis-loss/active-attempt recovery and soak acceptance remains separate work.

The repository's Redis 7 deployment profile supports the chosen command contract. Unit tests simulate Redis queue semantics; they do not execute Lua against a running Redis service. PostgreSQL skip-locked behavior, real Redis execution and production-stack acceptance are not certified by those mocks. No existing Redis, Agent Hub, production database, media or credential configuration was changed.

Fixture provider state now reflects the current fixture switch; the Studio disables fixture collection when the declared state is disabled. Other defaults remain: no external collection or publication is enabled by implementation, analytics produces recommendations, and billed costs are null until known.

Durable recurring refresh plans, their Owner controls, versioned AnalyticsProfile/operator integration, Native Studio analytics and real provider acceptance remain required. These guards complete part of that foundation. `ANALYTICS_READY = NO`; `PRODUCTION_HARDENING_READY = NO`.
