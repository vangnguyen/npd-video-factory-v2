# Publish consent and durable dispatch

This is an inert application persistence prerequisite. It neither enables the official publishing factory nor sends a network request. `PUBLISH_ENABLED=false` and the existing production approval behavior remain unchanged.

`PublishingDispatchJournal` requires separate, explicit publish-only consent from a current registered human Owner. The trusted internal caller supplies an already verified principal, the exact request fingerprint, the exact output SHA256 and acknowledgement. A freshly loaded `HumanAuthVerifier` rechecks the same token ID, subject, workspace role and identity revision. Missing registry, disabled/expired identity, role change or credential rotation fails closed. Only token IDs and identity fingerprints are persisted; bearer credentials are not.

Consent binds workspace, project, publication, production package and approval, current timeline/audio/subtitle versions, latest ready final render, passed QC, output asset checksum/size, metadata fingerprint, platform and provider. The source rights inventory is revalidated. A distinct idempotency key returns the same consent and deadline on repeat; it never extends consent silently. Consent lasts at most one hour and cannot outlive the human token. Revocation is idempotent and grants no remote cancellation/deletion permission.

The additive `0019_ns_publish_dispatch` migration creates `publication_publish_approvals` and `publication_dispatches`. It does not rewrite/backfill existing tables or create approvals for historical projects. Its destructive downgrade refuses execution pending an Owner-approved evidence export/recovery operation. The checked rehearsal applies the upgrade only to a new owned SQLite fixture; PostgreSQL migration and production rollout are not accepted.

Before an upload initiation or chunk, the journal rechecks consent, identity, current approval/QC/rights and binding. It commits a versioned intent and content-free audit event before returning a private worker ticket. A conditional update lets one worker claim a given version. The private nonce, lease and session reference are absent from public status and events. The ticket is an internal capability and must never be exposed through an HTTP response or browser store.

Initialization is permitted only once per publication. A missing initialization response becomes `init_uncertain`; process restart or lease expiry cannot issue another initialization POST. The Owner must reconcile the external outcome before any separately reviewed recovery design can admit a new operation. No such recovery/reset endpoint exists here. A known upload session is an opaque `pss_` reference, not an upload URL in the database.

Chunks are contiguous from confirmed acknowledged bytes. Unknown chunk outcomes require querying the same session. An active chunk/query lease prevents another claim; after expiry a fresh query ticket fences stale worker replies. Interrupted queries can be queried again after lease expiry. Reconciliation can record an already performed outcome after consent expiry/revocation; another chunk still requires fresh valid consent. Lease fencing prevents stale database writes, but an adapter must serialize/cancel its network work; a database lease alone cannot cancel an in-flight provider request.

Confirmed completion needs both all acknowledged bytes and a scoped provider receipt ID. `uploaded` does not mean processing succeeded or the video was published. Malformed/noninteger/oversized progress, raw session URLs and stale tickets are rejected. Recorded outcomes explicitly retain whether the parent is mocked; the journal does not infer a real external action from a fixture callback.

`north_star_publishing_dispatch_contract.py` retains seven evidence exports from fresh owned databases. It demonstrates committed intent before a simulated provider callback, competing claims, three separate Python process reads, lost chunk response reconciliation, consent revocation, permanently ambiguous initialization and additive migration preservation. Every human identity/consent, production approval, render/QC and provider receipt is a fixture. The real operations are SQLite transactions, filesystem persistence and process restart. No real provider, credential, paid operation, Owner UAT or production schema is involved.

Remaining work includes encrypted durable private session storage, verified storage bytes before transmission, fresh atomic source admission across concurrent edits, OAuth lifecycle, budget/cost capture, actual provider dispatch, complete processing/status/receipt integration, consent renewal/recovery policy, thumbnail upload and Native publishing UI/scheduler. YouTube/TikTok/Meta official adapters and real account acceptance remain unfinished. Neither Publishing nor the North Star is complete.
