# Native official account review

Master Spec sections 45–49, 52, 55/56 and Waves 8/9/10 remain authoritative. This increment adds explicit read-only account checks to the accepted Native Studio runtime. Official publishing, collection of real audience metrics, OAuth acquisition/refresh, Meta adapters, independent account acceptance and Owner UAT remain separate work.

The runtime reuses the existing provider-neutral target binding, bounded HTTPS transport and account-confirmation contracts. YouTube checks use `channels.list` with `mine=true`; exactly one returned channel must match the frozen target. TikTok checks use `/v2/user/info/?fields=open_id`; the returned application-scoped OpenID must match the target. The API contracts come from the official [YouTube account endpoint](https://developers.google.com/youtube/v3/docs/channels/list) and [TikTok user-info endpoint](https://developers.tiktok.com/docs/en/tiktok-api-v2-get-user-info). Provider responses are never replaced with fixtures when credentials or configuration are missing.

Both platform targets bind workspace, publishing-profile ID/version, provider key, account ID and a stable credential-binding fingerprint. A bounded, duplicate-key-rejecting external registry adds an account reference, credential alias, absolute token mount and explicit read enablement. Publishing remains strictly false; numeric values cannot substitute for that flag. The registry and token mount remain outside Native state and its backups; the token mount must also remain outside the source checkout. Linked and hard-linked paths are rejected. Configuration, client, transport, endpoint identity, root and resolver are frozen and checked before and after dispatch, including the final database transaction.

Windows access-token storage uses a separate DPAPI entropy domain and private file ACL, with an atomic create that refuses to overwrite an existing token. The typed token binds workspace, alias, platform, stable binding, supported read scopes and an explicit timezone-aware expiry. Invalid ciphertext, foreign bindings and resolver errors return sanitized codes. Public configuration, HTTP requests, history and logs contain no token or private mount path. The existing AssemblyAI DPAPI domain and default behavior remain covered by regression tests. An approved secret resolver can be injected without coupling the core to Windows paths.

Default startup performs no token decryption or account request. `--official-account-registry` supplies public configuration; `--enable-official-account-reads` additionally requires protected registry configuration and human authentication. Each actual read still requires a saved, current, idle project and an explicit Owner intent through `POST /api/projects/{id}/official-accounts/{account_ref}/verify`. The body contains revision, expected configuration SHA256, strict read-only acknowledgement and an idempotency key. It accepts no OAuth secret, arbitrary endpoint or publishing grant. Shared authentication, manage permission and CSRF validation occur before body processing. Viewing scoped history uses read permission.

The account-check queue persists an immutable project/document/target/configuration/request snapshot. Exact retries reuse the same check, including after subsequent project edits; conflicting requests reject. A worker records one bounded read and a cost dispatch intent. Each fresh explicit check uses a check-scoped ledger operation, so another Owner check in the same project can create its own record. Exact retries keep the original operation and cannot resend. Historical operations remain unchanged. Estimated and actual costs remain null when unknown. Provider failures, expired or insufficiently scoped credentials, changed project/configuration and foreign-account responses cannot produce a successful result. A successful result binds the response hash, account proof, cost-operation ID, mock/external-call flags and immutable snapshot. Rehashed mock evidence cannot be relabelled as an external read. This proof never grants publishing authority or changes project media, timeline, production jobs or approval.

Interrupted running checks become `outcome_unknown` on recovery. There is no automatic resend; a fresh explicit review is required. Completed history is retained even if credentials/configuration later change. History pagination is bounded and workspace/project scoped. Queued or running checks prevent offline backup; finished check rows and audit events are included in database snapshots. Secrets and the external registry are excluded. Recovery therefore requires separately configured protected credentials, without copying them into project archives.

Studio adds a capability-gated account panel with explicit configuration read, account selection, read-only acknowledgement, verification and paginated history. It makes no automatic request, accepts no secret and offers no publishing action. Saved/idle/project/Owner gates disable verification; viewers can read history. Unknown HTTP outcomes retain the same key for an explicit retry. Workspace, project, revision and role changes discard late responses. Untrusted labels and evidence use text nodes.

The Native read registry currently supports YouTube read scopes and TikTok `user.info.basic` plus `video.list`, anticipating the existing analytics contracts. YouTube reports additionally require the analytics scope and monetary scope for revenue, as described by [YouTube Analytics reports](https://developers.google.com/youtube/analytics/reference/reports/query); TikTok video counters require the authorized-user video contract in [TikTok video query](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-query). This increment does not request reports, inspect audience metrics or attach a fixture publication to an official analytics query. Expired tokens fail before dispatch; acquisition, secure refresh/rotation and provider-specific official publication receipts remain gaps.

Tests cover actual Windows DPAPI round trips and domain separation, strict tokens/flags/timezones, duplicate/foreign registries, absolute/private mounts, frozen configuration/wire changes, default disabled behavior, one explicit account read, idempotency, project edits before/during response, foreign-account rejection, immutable history, strict mock evidence, restart recovery, signed roles/CSRF before body parsing and scoped pagination. Studio tests cover zero startup calls, explicit saved Owner requests, unknown-outcome retry keys, viewer history, foreign evidence and late-response isolation.

The retained rehearsal restores the prior genuine local media bundle into fresh owned roots. Signed identities, access tokens and account responses are explicitly synthetic fixtures. Actual local DPAPI, SQLite, HTTP, cost history and both-database backup/restore are exercised; a fresh process verifies unchanged account history, project/jobs/media and explicit fixture token decryption without account dispatch. Machine evidence is indexed in `docs/north-star/native-official-account-evidence.json`. There is no real account verification, audience observation, new render/inference, paid operation, external provider call, legal acceptance, Owner UAT, production deployment or publication.

Continue official Native publishing and analytics runtime integration, protected OAuth refresh/rotation, Meta coverage, real-provider acceptance and all remaining original Mode A/B capabilities. An account check alone does not complete Waves 9/10 or enable publication.
