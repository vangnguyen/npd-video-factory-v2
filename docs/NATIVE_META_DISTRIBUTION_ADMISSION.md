# Native Meta distribution admission

This closes a backend component of Waves 8/9, against the original Master Spec. It does not complete Publishing, Mode A/B, a wave, or North Star acceptance. Facebook Page Reels and Instagram Reels use the Facebook Login Page credential architecture already introduced in `NATIVE_META_ACCOUNTS.md`.

`MetaCreate` is a separate tagged request. It requires exact original dry-run, current account check/result and configuration hashes. Client metadata overrides, tokens, arbitrary endpoints, API versions and account replacements are rejected. The completed dry-run must bind the same current canonical project, physically approved final, rights and platform validation. Metadata is reused exactly. Scheduling and custom thumbnails remain unsupported; Instagram requires public privacy, and Facebook accepts only the privacy supported by its pure protocol preflight.

`NativeMetaPublishingFactory` binds the exact account factory, Page/Instagram profile, cipher and configuration hashes, explicitly reviewed options and independent default-off gates. The protected companion registry has strict workspace/account bindings, a bounded manifest and drift checks. Loading this registry decrypts no token and sends no request. `CONFIGURED` describes admission prerequisites only; `execution_supported=false` and `external_actions_enabled=false` remain explicit and immutable.

The existing Native publication journal owns immutable snapshots, same-final/account duplicate protection, request idempotency, finite current human Owner grants, renewal/revocation/cancellation and prepared dispatch history. No database migration or new Meta-specific table is introduced. Account checks and dry-run receipts are never publish authority. The account's finite read-consent window is checked at initial review. Later renewal preserves that historical proof; the separate current Owner grant controls local admission. Actual credential validity and fresh provider preflight will also be required at the future send boundary.

Historical reads validate the original dry-run and account/cost foreign keys without current media or private credentials. New review or admission still revalidates the current canonical project and physical final. Rehashed authority/permission claims, borrowed cost evidence, replaced finals and unsupported provider execution/receipt evidence are rejected. The factory cannot return a publishing credential; the shared worker rejects Meta before any publish intent or network mutation. Frozen snapshots also bind `execution_supported=false`, so future activation cannot implicitly reuse these reviews/grants.

Existing signed HTTP routes accept the tagged request when this exact factory is explicitly bound in the owned fixture. Owner role and CSRF are enforced before body parsing. The component has actual local DPAPI/SQLite, signed loopback, public backup and separate-process default-off/keyless recovery evidence, using explicit Owner/platform/provider/nonplayable-media mocks. The HTTP fixture binds the factory directly; Native startup/CLI and the Studio Meta publication controls are not wired at this milestone. Current YouTube/TikTok behavior remains available by default.

Evidence: [`north-star/meta-admission-evidence.json`](north-star/meta-admission-evidence.json), `tests/test_meta_distribution.py`, `tests/test_meta_distribution_http.py`, and `scripts/north_star_meta_admission.py`. Counts and source preservation are recorded there and in the external recovery receipts; log files are retained rather than overwritten. No real provider permission, application eligibility, public post, genuine media/Owner/browser acceptance or production deployment is inferred.

Next safe work is durable Meta media delivery, upload/container/status/finish and receipt recovery, followed by protected runtime/CLI, shared queue and typed Studio controls. Fresh provider/account/rights/Owner enablement is required before real publishing. Continue every remaining original Master Spec gap and A/B/C acceptance independently; unavailable credentials are not a reason to stop safe implementation.
