# Official publishing wire protocols

This increment implements bounded HTTP transport and the YouTube resumable request/response protocol. No application factory activates it. `OfficialPublishingProvider` stays contract-only, `PUBLISH_ENABLED=false` and external/Owner execution gates remain false. Real publishing, deletion, OAuth configuration and deployment require their separate acceptance and Owner authorization. The protocol helpers produce requests; callers must supply validated artifacts, metadata, disclosures and existing authorization before dispatch. They do not claim to be a complete PublishingProvider.

The transport is restricted to fixed official origins per platform, with TLS verification, no environment proxy, cookies, redirects or automatic retries. Its network mode is disabled by default; only `httpx.MockTransport` can be injected for tests. OAuth tokens belong in headers; token/key query parameters are rejected. Opaque provider upload session URLs remain private. Request/response representations omit bodies, headers and URLs, exceptions expose fixed codes, and context-local HTTP library filters suppress sensitive wire logs without suppressing unrelated traffic. Requests, streamed responses, headers, timeouts and connection counts are bounded. Compressed responses are rejected before decoding.

YouTube supports metadata preparation, official session initiation, chunk requests, upload-status queries, confirmed completion, processing-status lookup and a deletion request builder. Category and child-directed/synthetic-media disclosures must be explicit. Title, UTF-8 description byte length, tags, privacy and future scheduling are checked. Caption and hashtags are preserved in description. The 512 MiB upload limit is an internal safe profile, not a vendor limit. Thumbnail selection fails explicitly until its separately approved stage is implemented.

[Google's resumable upload specification](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol) defines session initiation, continuous chunks and recovery by querying the same session after interruption. The parser reports acknowledged offsets, completion only with a valid video ID, bounded retry delays and uncertainty. Expired sessions require review; helpers never start another session automatically. No vendor idempotency header or server deduplication guarantee is invented. [Video resource metadata](https://developers.google.com/youtube/v3/docs/videos) defines title/description/tag constraints, disclosures and scheduling semantics. [Video insertion](https://developers.google.com/youtube/v3/docs/videos/insert) also documents account/project audit restrictions. [Deletion](https://developers.google.com/youtube/v3/docs/videos/delete) is a distinct irreversible action; its request builder grants no authorization.

TikTok's verified API/upload origins are reserved in the transport. Its signed upload URL cannot receive the OAuth bearer header. The actual TikTok creator-consent, initialization, chunks and status implementation remains pending, following the [official Direct Post contract](https://developers.tiktok.com/docs/en/content-posting-api-reference-direct-post). Meta adapters remain pending; no protected-platform scraping or browser automation is used.

Required next integration: durable workspace/project/approval/artifact-bound dispatch intent **before any mutating request**, private encrypted session references, exclusive worker claims, ambiguous-outcome reconciliation without repeated initiation, scoped verified storage bytes, fresh rights/QC/Owner Publish Approval, OAuth lifecycle, provider cost capture, scheduler/history and Native Studio UI. These are implementation gaps; missing provider credentials do not waive them. A protocol test does not prove a post survives process restart or duplicate execution.

Evidence: `north-star/publishing-wire-evidence.json`. Tests exercise actual HTTP request composition against mock transports, unsafe origins/headers/redirects, private exceptions/logs, bounds, Vietnamese metadata, chunk acknowledgements and status parsing. The isolated fixture creates and fully decodes a synthetic H.264/AAC MP4, transfers identical bytes to a mock receiver, loses the final response and then queries the existing session. Exactly one initialization POST occurs. Its video ID and receipt are fixtures; no real post, Owner review, production acceptance or full publishing readiness is claimed.
