# Windows object-storage path handling

Valid portable object keys could exceed Windows MAX_PATH after being combined with a local storage root. A retained baseline reproduced FileNotFoundError/WinError 3 at a 313-character valid root. The API local provider and private publishing-artifact reader now normalize absolute filesystem paths before using the Windows extended I/O prefix. UNC conversion is tested as a pure path contract without accessing a share. Portable keys, their 768-character limit and public storage roots remain unchanged. POSIX paths are passed through. The change does not alter machine policy or make S3/production depend on a Windows drive.

Local and S3 filesystem copies use unique short temporary names, so concurrent writes do not share a temporary file and a valid 255-character destination filename needs no overlong temporary name. Local copies flush and fsync before atomic replacement; failures preserve the previous destination and remove only the owned temporary. Local receipts describe the actual stored bytes, including when the input changes after copying. The private publishing reader retains bounds, no-link/hard-link, checksum and range-change checks. Its Windows I/O conversion follows the original parent-traversal rejection.

Current related API verification executed 200 passing checks, initially skipping seven publishing-worker AES fixtures because the shared verification runtime lacked the repository's declared optional cryptography==50.0.2 dependency. That pinned package was installed from official PyPI into the private C:/vf-object-storage-test-deps-01 target, without modifying the shared Native/API/Agent Hub runtimes. The seven fixtures then passed separately, with explicit mock QC/OAuth/account/provider transport. All 207 checks have executed successfully; this is not real publishing or genuine S3 acceptance. The 25 new storage checks include actual long local roots and sources, the 768-character key boundary, interrupted/concurrent copy behavior, stored-byte receipts, a 255-character filename, traversal/namespace refusal, an actual local NTFS junction escape check, private checksum/range and hard-link guards, and an explicit S3 SDK filesystem mock.

A retained real-local rehearsal reads one original accepted Phase 8 artifact, stores it under a 334-character logical root and 463-character private I/O path, downloads it, and verifies private bounded/range admission. Source, stored, downloaded and private bytes match SHA256 3de523aff48851e8af293ae32eb202399f14089ab3025e257a568479367c66ba at 4,213,829 bytes. A fresh process reopened the same portable key and recovered identical bytes without a provider configuration or credential. The accepted source was read only and never replaced. This byte-preservation proof performs no new render or full media QC and does not replace the original media acceptance or Owner UAT.
