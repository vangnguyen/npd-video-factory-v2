# Finite Native official publication queue kernel

Wave 9 adds `NativeOfficialPublicationQueue`, a default-disabled Native scheduling kernel. Runtime/HTTP/Studio controls are the next increment; this library is not automatically attached to the existing Runner. Approval of a publication alone creates no queue plan and sends no provider request.

`QueueCreate` requires the exact reviewed snapshot and dispatch version, a separate literal `acknowledged_background_steps=true`, 1–100 steps, an interval of 30–3600 seconds, explicit timezone-aware start/deadline and an idempotency key. The window must fit inside both the existing publication grant and the current Owner's authority. Numeric/coerced acknowledgement, unbounded scheduling, unknown client gates/tokens/endpoints, stale versions and conflicting keys are rejected. One queued/running plan is allowed per publication. Exact key replay is a read of the original policy even after source changes.

The immutable policy binds workspace/project/publication/snapshot/approval, current queue Owner authority, mock qualification and finite limits. Three separate tables retain plans, step claims/results and events. Claims are atomic and consume an attempt before sending. One `process()` call performs one upload/reconciliation/processing step through the existing worker. Every wire request has an internal queue guard as well as current publication/grant/source/configuration checks. No client can supply that guard.

The queue observes the existing durable provider read backoff. Known 429/5xx reads may schedule another bounded attempt. Uncertain responses stop the plan for review, with no automatic new initialization or repeated bytes. An Owner may create a new explicit plan to reconcile a known session; expired or revoked publication consent still requires separate renewal. A new grant invalidates the old queue policy. Step exhaustion, deadline/Owner/source/grant changes and interrupted claimed work stop execution. Startup recovery is local only, after existing publication-worker recovery; it neither decrypts credentials nor sends/renews.

Queue cancellation stops this plan's future steps and preserves known in-flight responses. It does not revoke the publication grant or remotely delete a video. Publication-level **Dừng quyền gửi** remains the action that revokes all future publication authority. Queue guards prevent cancellation during account verification from initiating an upload. A known initialization reply can be retained after queue cancellation; a valid known chunk reply can retain acknowledged progress. If publication consent itself is revoked, chunk progress remains unconfirmed and no processing receipt can be issued.

Historical plan/results are read without configured credentials, providers, private-session vault or queue enablement. Results are strict typed records containing phase/version/bytes, mock qualification and receipt hashes; no raw session URI, token or provider body is stored. Scope, hashes, ordinals, count, claim bindings and mock qualification are validated before further sends. Backup busy detection and counts include all three queue tables.

Retained rehearsal: `scripts/north_star_native_official_publish_queue.py`. A separately authorized first plan initializes and encounters an explicitly simulated lost first-chunk response. It stops and does not retry itself. A new explicit plan reconciles the same session and finishes with a qualified mock receipt. There is one initialization, three unique data chunks, one reconciliation, 12 mock provider requests, two preserved plan histories and exact recovery of all fifteen journals, original project/dry run/job/physical artifacts and preceding revocation receipt. Backup excludes protected credentials/session files and private URLs. Fresh-process recovery leaves the queue disabled.
