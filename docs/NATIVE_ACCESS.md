# Native Studio access

The accepted loopback Owner mode remains the default for the existing Windows installation. An operator can explicitly configure hashed human identities with `--auth-registry <external-profile.json> --workspace-id wsp_<id>` on `python -m services.windows_native.server`. Both arguments are required together. The registry uses the existing `vf1` identity schema in `apps/api/app/human_identity.py`; it contains hashes, enabled/issued/expiry fields and workspace roles. It stores no raw access tokens. This change neither creates credentials nor enables access on the live installation.

Configured mode requires sign-in at `/login`, then a random, HttpOnly, SameSite=Strict, loopback session cookie and a distinct in-memory CSRF token. The password field is cleared before login waits for a response. Neither bearer credentials nor sessions are stored in browser storage or passed in URLs. Session metadata exposes only the authenticated identity, role, workspace and permissions. Logout revokes its own session. Restart, expiry or any registry content change invalidates sessions. Missing/malformed/oversized configuration fails closed; it cannot become a local Owner session. The registry must remain outside the state directory and links, junctions and hardlinks are rejected.

| Role | Permissions |
| --- | --- |
| owner | Read, edit, review; credentials, diagnostics, cost policy and opening output folders |
| editor | Read and edit; approval and administrative actions denied |
| reviewer | Read and review; project edits and administrative actions denied |
| viewer | Read; mutations denied |
| service | Separate versioned Agent Hub service identity; human login rejects service tokens |

Every API request is authorized before dispatch or body processing. POST routes are an explicit allowlist and unknown mutations are denied. Existing Host/origin checks, immutable versions, CAS, idempotency, rights, budget and human approval checks still run after authorization. Review and supplied actor fields are bound to the authenticated token ID rather than a caller-selected name. A role cannot waive acknowledgements, approve a different revision/hash, turn script approval into production approval, enable publishing or invoke an unconfigured provider. All tests use explicit fixture identities and do not record actual Owner UAT.

One Native state directory is bound to one workspace with `.vf-auth-workspace.json`. Initial configured startup writes this small, non-secret marker; subsequent binding must match it exactly. Startup without a configured registry is rejected for a bound state root, preventing an omitted flag from bootstrapping a local Owner. No database schema or existing project is rewritten. The marker is included by the existing backup/restore path. Changing or deleting it fails closed during configured operation and invalidates sessions; changing workspace identity requires an explicitly reviewed recovery/migration rather than relabelling another workspace. Native remains one workspace per state root; PostgreSQL mode provides its own workspace model. Production multi-user/network acceptance remains separate.

The four Studio pages optionally load the session badge, logout and permission controls only when the backend returns `access.mode=registry`. Unknown roles fail closed. Controls respect read/edit/review/manage independently, including controls created after startup; capture guards and reapplication after page state changes prevent stale enabled buttons. HTTP authorization remains the security boundary. Existing local Owner/older server capability paths continue without the new auth module. Session expiry sends configured Studio back to the fixed login page without replaying writes. Owner-only settings HTML returns a permission error for other roles.

Limits are bounded in code: at most 256 sessions, one hour maximum session TTL, ten shared login attempts/minute and 600 requests/session/minute by default; registry at most 256 KiB/512 records. Profiles are checked again during authorization/readiness and new roles require sign-in. `/healthz` remains a process-liveness probe; `/readyz` now includes a boolean configured-auth check, exposing no paths, identity or secret. Public static modules contain no application state. Loopback HTTP transport is retained; no production network, TLS, credential issuance/rotation UI, API role-policy rewrite or service-auth integration is claimed.

Evidence: `docs/north-star/native-access-evidence.json`; actual isolated HTTP/session/SQLite acceptance from `scripts/north_star_native_access_contract.py`, security tests and Node login/permission-control runtime tests. Node DOM fixtures do not certify browser layout at 1366/1920/2560, non-developer UAT or production deployment. Those and real-provider acceptance remain pending.
