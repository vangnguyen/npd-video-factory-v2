# Master service API /v1

The SQL/API runtime now exposes all18 example operations in Master Spec section53, using the existing project, upload, analysis, trend/idea, content-generation, canonical timeline, preview, production, approval, publishing and analytics services. Supporting chunk upload, timeline creation, content authoring/apply, production-package/review-render/approval request, job reads and protected media reads make the paths usable together. Existing /api/v1 human routes and legacy /api/v1/bridge contracts remain available; Native's draft/read /v1 boundary is not silently claimed equivalent.

Service access uses the existing agent-hub-bridge.v1 HMAC wire identity, with video-factory-service.v1 capability discovery. Protected identity configuration adds optional workspace_grants mapping exact workspace IDs to explicit capabilities. Empty grants confer no new service API access; wildcard workspaces, unknown/human role names and duplicate capabilities are rejected. A service key is never converted into a HumanPrincipal. Signature/nonce/exact body/path/query validation runs before JSON/model parsing; duplicate headers/JSON fields, oversized bodies, malformed constants and combined service/human roles fail closed. Structured errors do not echo invalid private raw bodies. Responses use no-store.

Each resource lookup checks its actual canonical project/workspace and the named capability. Upload parts support bounded32MiB signed bodies; JSON bodies are bounded8MiB. Actor refs are server-bound to the verified service or human identity. Content marked approved additionally requires a human reviewer. Production approval requires both scoped service authentication and the existing human reviewer/owner verifier; publication submission additionally requires human owner auth. Client reviewer/actor labels cannot confer authority. Final render remains bound to the existing current approval/timeline/subtitle/audio versions. Rights, QC, provider configuration, publishing profiles, default-off publishing and durable provider-cost/budget controls remain in the existing core.

Service commands persist only the idempotency/request digest and a scoped immutable response receipt, not keys or human tokens. Exact retries return the original response. Different method/path/query/payload/actor under the same key conflicts. Concurrent reservations have a database uniqueness boundary. Cached-response tampering is rejected. If canonical mutation succeeds but receipt completion is interrupted, the operation becomes uncertain and retries never redispatch it. Its diagnostic route exposes the persisted outcome state under the original service/capability. Automatic reconciliation of such outcomes remains an explicit gap; callers must inspect the canonical result rather than create a new key blindly.

Trend refresh performs existing collection plus cluster/opportunity queue processing with configurable context. Idea generation remains the existing recommendation engine; content generation queues an existing proposal job and requires explicit apply/review. It does not approve content automatically. No fictitious trend metrics or creative-provider claims are introduced. Preview/render polls return service-accessible /v1 playback links without changing canonical records. Protected content routes reuse storage/asset lookup and temporary-download cleanup.

The optional Hub boundary now initializes atomically. Invalid or missing service/signing custody disables only the Hub boundary as not_configured; the human/core API remains usable. No Hub network/process availability is required to produce/edit videos. Additive migration0025 creates service_api_operations and preserves existing rows/schema; it was exercised only in a new owned SQLite DB. Destructive downgrade is refused. No live/production migration, infrastructure change or deployment was performed.
